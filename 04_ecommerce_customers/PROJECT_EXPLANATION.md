# E-commerce Customer Analysis: project explanation

## 1. Business question
How often did identifiable customers place another invoice within a comparable 90-day observation period?

## 2. Source and scope
Chen, D. (2015), Online Retail, UCI Machine Learning Repository, https://doi.org/10.24432/C5BW33 (CC BY 4.0).

Source documentation: https://archive.ics.uci.edu/dataset/352/online+retail

The source is invoice-line data from a UK online retailer, 1 Dec 2010 to 9 Dec 2011. This analysis groups positive lines into customer/invoice purchases.

Included raw file: `raw.csv.gz`. SHA-256: `95e7ce0123134e1a0c44aeb0fc1632048a35a1c96d5d57ec727534ae6d02d27d`.

The included compressed CSV is a conversion of the original UCI workbook. Both retail projects use the same source for different questions; they are not independent datasets.

## 3. Data dictionary
- InvoiceNo and CustomerID: identifiers used to construct a customer/invoice order.
- InvoiceDate: date and time of the transaction.
- Quantity and UnitPrice: invoice-line quantity and unit price in pounds.
- line_value: Quantity × UnitPrice for qualifying lines.
- first_day, eligible_90d and repeat_90d: derived customer-level fields in outputs/customer_summary.csv.

## 4. Cleaning and quality checks
541,909 source lines; 9,288 cancellation-prefixed lines; 11,805 nonpositive quantity or price lines; 11,805 excluded by either rule; 135,080 source lines lack customer ID. These categories overlap. 5,268 exact duplicate-looking rows are retained because they may represent distinct invoice lines. Among otherwise qualifying lines, 132,220 lack customer ID and are excluded from customer metrics.

Review `data/clean.csv.gz` for the analytical records. Duplicate-looking records are not removed without a reliable event identifier. `unknown` categories are retained where present. Quality rules are explicit in `project.py`.

## 5. Metrics and definitions
- An order is a distinct CustomerID and InvoiceNo combination in the cleaned data.
- Average invoice value = total included line value for identified customers ÷ distinct identified customer/invoice orders.
- First observed purchase is the earliest included invoice in this dataset, not necessarily a lifetime first purchase.
- 90-day repeat rate = eligible customers with at least two distinct invoices by 90 calendar days after first observed purchase ÷ eligible customers.
- Eligible means first observed purchase is at least 90 calendar days before the final observed date. Same-day distinct invoices count.

## 6. Results
| Metric | Value |
|---|---:|
| Identified customers | 4,338 |
| Identified invoices | 18,532 |
| Average invoice value | £480.87 |
| 90-day repeat rate | 47.7% |

### Findings
1. 1,607 of 3,370 eligible customers made a second observed invoice within 90 calendar days.
2. Average identified invoice value was £480.87, excluding cancellation and nonpositive lines.
3. 132,220 otherwise qualifying lines lack customer IDs and are excluded from customer analysis.

Detailed segment counts and values are in `outputs/`. Percentages in text and slides are rounded; CSVs retain greater precision.

## 7. Recommendation
Test a post-purchase message using a randomized holdout and track 90-day repeat purchases and contribution margin among eligible customers.

### Next steps
1. Reconcile returns and join earlier order history to distinguish new customers from first observed customers.
2. Compare mature cohorts over equal follow-up windows and segment wholesale accounts separately.
3. Randomize a retention intervention and measure incremental gross profit after message costs.

## 8. Limitations and interpretation
Only identified transactions are included. The dataset has no pre-window customer history, and the source is a gift retailer with wholesale customers. Cancellation and negative lines are excluded without matching to original invoices, so values are not net of returns. Observed repeat is not lifetime retention; customers may place orders outside the data window.

These findings describe the supplied historical data; they should not be presented as results for another company or as causal effects.

## 9. Reproduce the analysis
1. Install Python 3.9+ and the dependency: `python3 -m pip install -r requirements.txt`.
2. From the project folder, run `python3 project.py`. The included source file is read locally; no network connection is needed.
3. Review `outputs/summary.json`, the segment CSVs and `data/clean.csv.gz`. Re-running overwrites generated outputs and this explanation but preserves the raw source file.
4. Open `presentation.pptx`. The deck is a snapshot of this analysis and is not automatically regenerated by `project.py`.

## 11. Run the interactive dashboard

From a terminal opened in this project folder, create and activate a virtual environment, then install the dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

On Windows, activate the environment with `.venv\Scripts\activate` instead. The initial installation requires internet access. Then start the dashboard:

```bash
python -m streamlit run dashboard.py --server.address 127.0.0.1
```

Open the local URL printed in the terminal (normally `http://localhost:8501`). Stop the server with Ctrl+C. To run another dashboard at the same time, use a different port, for example append `--server.port 8502`. The dashboard reads the included local files and does not need internet access after installation. If an analysis output is missing, run `python project.py` first.

Filter customers by first observed purchase month and total observed invoices. The repeat-rate chart uses only customers with a complete 90-day observation window. Restricting total invoices selects customers using later behavior, so the resulting repeat rate describes that selected group only. Download the eligible cohort table as CSV.

Changes to filter selections affect the dashboard only. Run `python project.py` to rebuild the cleaned data and analysis outputs from the included source; the dashboard detects the updated files. The presentation remains a separate snapshot and is not rebuilt by the dashboard or analysis script.
